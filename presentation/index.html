tex4npm

A webpack-style build tool for Ximera

LaTeX → HTML via the conceit of npm packages and an Elm-architecture runtime

What problem does it solve?

Authors write interactive math courses in LaTeX using the ximera document class.

tex4npm compiles those .tex files to interactive HTML — like webpack, but for LaTeX.

Modeled on the webpack developer experience:
declare dependencies in package.json,
configure via tex4npm.config.js,
run via npm scripts. 
my-course/
├── package.json
├── tex4npm.config.js
├── src/
│   ├── intro.tex
│   └── chapter1/
│       └── limits.tex
└── dist/          ← compiled output
    ├── ximera.js
    ├── ximera.css
    └── src/
        ├── intro.html
        └── chapter1/
            └── limits.html

npm packages carry LaTeX and JavaScript

A package like my-button declares both its .sty file and its client-side JS in one package.json.

// my-button/package.json
{
  "name": "my-button",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "latex": {
    "sty": ["my-button.sty"]
  }
}
% my-button/my-button.sty

% PDF mode: box around text
\newcommand{\button}[1]{\fbox{#1}}

% HTML mode (tex4ht): native element
\ifdefined\HCode
  \renewcommand{\button}[1]{%
    \HCode{}%
  }
\fi
The "latex" field is the signal. sty lists LaTeX packages; css lists stylesheets to bundle. tex4npm discovers every installed package that has this field.

High-level build pipeline

Each npm run build runs three phases:

① Pre-build (stage)
→
② Bundle (esbuild)
→
③ Compile .tex files
① Stage
Scans node_modules for "latex" packages, symlinks .sty files so TeX can find them, writes a JS bundle entry file.
② Bundle
esbuild bundles all package JS and CSS into dist/ximera.js and dist/ximera.css.
③ Compile
For every dirty .tex file: run the full LaTeX→HTML pipeline, then post-process the HTML. Parallelised with a concurrency queue.

Pre-build: the stage phase

Runs once per build invocation before any .tex file is touched.

Stage 1 — Discover packages
fast-glob finds all node_modules/*/package.json. Filter to those with a "latex" key.
Stage 2 — Populate .tex4npm/texmf/
Wipe and rebuild .tex4npm/texmf/tex/latex/. Symlink each declared .sty file into that directory. Injected via TEXINPUTS=.tex4npm/texmf//:… at compile time.
Stage 3 — Write .tex4npm/bundle-entry.js
One import 'package-name' per discovered package, plus CSS imports for any declared .css files.
Stage 4 — Run esbuild
Bundle the entry into dist/ximera.js + dist/ximera.css. Sub-second; runs unconditionally every build.

How .sty files reach LaTeX

.tex4npm/
└── texmf/
    └── tex/
        └── latex/
            ├── my-button.sty  →  ../../node_modules/my-button/my-button.sty
            └── ximera-core/   (no sty — JS/CSS only)

TEXINPUTS=.tex4npm/texmf//:<original>

The // suffix tells kpathsea to search recursively. LaTeX finds every staged .sty without touching the system TeX installation.

Symlink → live edits
Symlinks are preferred so that edits to a locally npm linked package are immediately visible without re-running the pre-build phase.
Hard link fallback
Used when symlinks require elevated privileges (Windows).
Copy last resort
Cross-drive or restricted filesystems.

Per-file compilation pipeline

Every eligible .tex file (contains \begin{document}) passes through four steps. All run with cwd = the file's directory.

1 pdflatex
→
2 latex ×2
→
3 tex4ht
→
4 t4ht
1 — pdflatex
With tikzexport and xake class options. Generates .aux, PDF, and .fls (recorder).
2 — latex ×2
tex4ht.sty injection preamble passed as a single argument. First pass generates .4ct/.4tc hook files; second uses them to emit HTML into the DVI.
3 — tex4ht
Converts DVI → HTML. Config: ximera,charset=utf-8,-css. Writes stem.lg listing every file it produced.
4 — t4ht
Post-processes stem.lg: CSS output, image handling, other file generation.

The tex4ht.sty injection trick

Instead of invoking htlatex as a shell-script wrapper, tex4npm calls latex directly with the injection preamble extracted verbatim from the htlatex source.

latex -recorder -interaction=nonstopmode -shell-escape \
  "\makeatletter\def\HCode{...}\def\Link#1.a.b.c.{%
     \g@addto@macro\@documentclasshook{%
       \RequirePackage[#1,html]{tex4ht}}...}%
   \makeatother\HCode ximera,charset=utf-8,-css.a.b.c.\input stem"
Why? htlatex is a shell script that itself calls latex with this preamble. By calling latex directly, tex4npm controls every flag (especially -recorder for the .fls dependency log) without subprocess indirection.
Exit code caveat — latex exits with code 1 even on successful DVI production when there are recoverable warnings. tex4npm uses reject: false (execa) and lets the downstream tex4ht step fail if no .dvi was actually produced.

Incremental builds: dirty checking

tex4npm avoids recompiling files whose dependencies haven't changed.

<!-- injected into <head> after each compile -->
<meta name="dependency"
  content="a3f9c2... src/intro.tex">
<meta name="dependency"
  content="7b1e4d... src/shared/macros.tex">
<meta name="dependency"
  content="f02c89... .tex4npm/texmf/tex/latex/my-button.sty">

One tag per file that latex -recorder listed as an INPUT. Paths relative to the project root.

On next build:
Re-read existing .html, parse the dependency tags, SHA1-hash each named file on disk. If any hash differs (or the .html doesn't exist) → file is dirty.
Propagation:
If macros.tex changes, every .tex that inputs it is also marked dirty — without any special-casing.

Dependency graph & topological sort

Before compiling, tex4npm builds a DAG of \input, \activity, \include references between .tex files and sorts it topologically.

xourse.tex
  \activity{chapter1/limits.tex}
  \activity{chapter1/derivatives.tex}

chapter1/limits.tex
  \input{../shared/macros.tex}
macros.tex compiles first.
limits.tex and derivatives.tex compile next (in parallel).
xourse.tex compiles last (it reads activity <title> and <abstract> from already-compiled HTML).
Concurrency model — the p-queue concurrency limit wraps only the execa subprocess calls (pdflatex/latex). Artifact copying, SHA1 hashing, and HTML post-processing run outside the queue, fully concurrent across all in-flight files.

Artifact collection & cleanup

Two separate sources of output files, because latex and tex4ht are separate binaries with separate output sets.

From stem.fls (latex -recorder):
INPUT lines → dependency metadata
OUTPUT lines → latex-side outputs
From stem.lg (written by tex4ht):
File: name lines → tex4ht outputs (HTML, SVG, PNG, CSS)
Artifacts copy to dist/
.html, .svg, .png, .css, .sagetex.sage
Temps delete
.aux, .dvi, .log, .4ct, .4tc, .fls, .xmjax, .xmcss, …

Artifacts mirror the source hierarchy: src/ch1/limits.svg → dist/src/ch1/limits.svg. Relative paths in HTML stay valid.

HTML post-processing (cheerio) 1 / 2

Each compiled .html in dist/ is parsed and transformed in sequence:

1 Remove empty <p></p> — spurious blank paragraphs emitted by tex4ht
2 Inject dependency metadata — one <meta name="dependency" content="SHA1 path"> per INPUT file from .fls
3 Inject .xmjax — filtered \newcommand definitions as <script type="math/tex"> for MathJax
4 Inject .xmcss — ad-hoc CSS (e.g. minipage widths) as a <style> block
5 Strip old CDN scripts — remove ximera.osu.edu <link> and <script> injected by ximera.cfg

HTML post-processing (cheerio) 2 / 2

6 Mark blocking problems — add data-blocking="" to every .problem-environment that directly contains at least one answerable
7 Inject bundle refs — append <link rel="stylesheet" href="ximera.css"> and <script defer src="ximera.js">
8 Enrich xourse links (xourse files only) — read the compiled activity HTML to inject <h2> title and <h3> abstract into each <a class="activity"> link

The .xmjax and .xmcss sidecar files

.xmjax — MathJax preamble

Generated by ximera.cls during the tex4ht pass. Every \newcommand and \DeclareMathOperator in the document gets written to this file.

Why? MathJax renders math in the browser but doesn't know the author's custom macros. The preamble is filtered (remove lines with :, @, \label, …) and injected as <script type="math/tex">.

.xmcss — ad-hoc CSS

Written by the \xmCSS{…} macro in ximera.cfg. Currently used for minipage width percentages computed in TeX.

Why? The HTML tag for a minipage is emitted before its width is known. The CSS file carries the computed value, which gets injected as a <style> block.

Both files are classified as temps — deleted after post-processing, never copied to dist/.

The Elm-architecture runtime (ximera-core)

The compiled ximera.js bundle implements a pure functional update loop.

DOM events
→ dispatch(msg) →
update(model, msg)
→ new model →
render(model)
→ data-state →
CSS
→
agent.setPageState
Model — flat object keyed by DOM element ID. Stores per-element state: { available, complete, correct, attempt, chosen, … }
update(model, msg) — pure function. Handles answer checks, choice selection, cascading problem unlock.
render(model) — only DOM writer. Sets el.dataset.state on each element. CSS reads data-state and drives all visuals.
agent — @modulus-learning/agent persists model to server via setPageState(model) and tracks progress with setProgress(0–1).

CSS state machine

All visual transitions are driven by data-state attributes. No inline styles. MathJax-safe: uses visibility + position instead of display: none.

/* Hidden until available */
.problem-environment[data-blocking] {
  visibility: hidden;
  position: absolute;
  opacity: 0;
  transition: opacity 0.4s ease;
}
.problem-environment[data-state~="available"] {
  visibility: visible;
  position: relative;
  opacity: 1;
}
/* Feedback */
.feedback {
  visibility: hidden;
  position: absolute;
  opacity: 0;
}
.feedback[data-state="visible"] {
  visibility: visible;
  position: relative;
  opacity: 1;
}

/* Correct answer */
.answer[data-state~="correct"] input {
  border-color: #4caf50;
}
Why visibility not display? MathJax needs to measure element dimensions to position math correctly. display:none removes elements from layout; visibility:hidden; position:absolute hides them visually while keeping them measurable.

Component packages — the registration pattern

Any npm package can hook into the runtime by calling register() on import.

// my-button/index.js
import { register } from 'ximera-core';

register('button', (el, dispatch) => {
  el.classList.add('ximera-button');
  el.addEventListener('click', () => {
    dispatch({
      type: 'BUTTON_CLICKED',
      id: el.id,
    });
  });
});
How it works:
  1. Package calls register(selector, mountFn) on import (synchronous)
  2. When the agent fires onReady(), the core iterates the registry and calls each mountFn(el, dispatch) once per matching DOM element
  3. mountFn attaches event listeners and can only call dispatch(msg) — it never reads the model directly
One-way data flow: events → dispatch → update → render → CSS.

Problem completion & cascading unlock

Replicates the old server's ximera:complete / ximera:answer-needed event chain, now as pure model updates.

problem1  [data-blocking]
  answer blank  ← \answer{17}
  feedback[attempt]
  feedback[correct]
  problem2  [data-blocking]   ← unlocks when problem1 complete
    answer blank
    problem3  [data-blocking] ← unlocks when problem2 complete

The data-blocking attribute is added by postprocess.js to every problem that directly contains at least one answerable.

propagateCorrectness(model, problemId)
  1. Find all direct answerables
  2. If ALL correct → set complete: true
  3. Mark attempt & correct feedback visible
  4. Set direct child blocking problems available: true
  5. Recurse to parent problem

Progress tracking

calculateProgress(model) mirrors the old server's recursive tree traversal.

function nodeProgress(el, model) {
  const state = model[el.id] ?? {};
  const children = directChildProblems(el);

  const selfValue = state.complete ? 1 : 0;
  if (children.length === 0) return selfValue;

  const childSum = children.reduce(
    (sum, child) => sum + nodeProgress(child, model),
    0
  );
  return (childSum + selfValue)
       / (children.length + 1);
}
Each node contributes its own completion (0 or 1) averaged together with its children's progress. Top-level problems are averaged to produce the final 0–1 float.
Sent to server:
agent.setProgress(calculateProgress(model))
called after every dispatch().
